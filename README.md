# Wren: a Pavona top kept outside Pavona

Wren is a small [Pavona](https://pavona.org) top (Ibex, 64 KiB flash, no OTP or lc_ctrl) for the
Digilent Genesys 2 FPGA board and Verilator. This repository holds only the top. It is a Bazel
module (`pavona_wren`) that uses a Pavona checkout as a dependency, so Pavona needs no line
naming Wren. It is also meant as the model for keeping any top out of tree: see "Making your own
out-of-tree top" below.

Only sources are committed. Everything Pavona's generators make from them is listed in
`.gitignore` and is made by `util/regen.sh`.

## Layout and prerequisites

The Pavona checkout must be next to this one, as `../pavona`:
```
<dir>/pavona   Pavona, with the out-of-tree fixes (until they are upstream: the exttop-* and
               hsw-* branches of github.com/mdhayter/pavona; use the stack tip)
<dir>/wren     this repository
```
`MODULE.bazel` points at it (`local_path_override(path = "../pavona")`), `.bazelrc` imports its
`.bazelrc`, and a few files here are symlinks into it (below). Set Pavona up as its
`doc/getting_started` says, including its Python venv.

## Build

```sh
source ../pavona/.venv/bin/activate
util/regen.sh                      # once after a clone, and after any change to the sources
../pavona/.bin/bazelisk test @pavona_pavona//sw/device/examples/hello_world:hello_world_sim_verilator
../pavona/.bin/bazelisk build //hw/top_wren/bitstream:fpga_genesys2    # needs Vivado
../pavona/.bin/bazelisk build //hw/top_wren/bitstream:fpga_genesys2_test_rom
../pavona/.bin/bazelisk test //hw/top_wren/sw/tests:hello_world_fpga_genesys2_test_rom   # Genesys 2 attached
```
Board tests live in `hw/top_wren/sw/tests/`: Pavona's tests ask for environments by role and
reach only Wren's Verilator environment, so Wren builds Pavona's test sources for its board
environments there. The first `bazel test` on the board synthesizes once more, for the test's
configuration (the universal splice, as Egret's tests use).

The second build is the bitstream with the test ROM spliced in (Vivado's `updatemem`, seconds once the
bitstream is built). Source the host's `vivado-env-*.sh` before every Bazel command, also those
that need no Vivado: the environment is part of the bitstream actions' keys, so a run without it
rebuilds them.
Use the checkout's bazelisk (its `bazelisk.sh` changes to its own directory). `.bazelrc` makes
Wren the top (`--@pavona_pavona//hw/top:top=wren`). Pavona's labels are
`@pavona_pavona//...` from here; Wren's are `//hw/top_wren/...`. For host options, see
`.bazelrc`.

## Sources and generated files

Committed (the sources):
- `data/top_wren.hjson`, `data/xbar_*.hjson`, `data/top_wren_seed.testing.hjson`: the top's
  description, which the generators read;
- `defs.bzl` (the top's `pavona_top()` and its attributes), the BUILD files, the `.core` files;
- hand-written RTL (`rtl/*.sv`), the chip level template `templates/chiplevel.sv.tpl`, the
  Genesys 2 constraints (`data/*.xdc`), lint waivers, Vivado hooks (`util/`);
- the Verilator testbench (`dv/verilator/`);
- device software that belongs to the top: `sw/test_pinout.c`, `sw/dt/`, `sw/arch/` (the
  Genesys 2 build's clock frequencies), `sw/autogen/chip/BUILD`;
- `util/regen.sh` and `util/fix-labels.py`.

Generated by `util/regen.sh` (git ignored): `ip_autogen/` (by ipgen), `ip/xbar_*/` (by tlgen),
every `autogen/` directory (by topgen and the top generators: RTL, DV, software, Bazel, the
complete configuration and host description) and `doc/memory_map.md` (by gen_top_docs).

Symlinks into `../pavona`, for files Wren shares unchanged with Egret: the AST and sensor_ctrl
IP descriptions and RTL (`ip/ast`, `ip/sensor_ctrl`), `templates/toplevel.sv.tpl`, some Vivado
hooks and lint files, and `third_party/*/patches` (below).

## Where build output goes

| what | made by | where |
|---|---|---|
| Generated sources (above) | `util/regen.sh`, run by hand | in this tree, under `hw/top_wren/` (git ignored) |
| Everything Bazel builds | `bazelisk build`/`test` here | this repository's own Bazel output base, reached through the `bazel-bin`, `bazel-out` and `bazel-testlogs` links here; not the Pavona checkout's |
| Wren's own targets (device software of `hw/top_wren`, the bitstream) | Bazel | `bazel-bin/hw/top_wren/...`; the bitstream's Vivado run in `bazel-bin/hw/top_wren/bitstream/build.fpga_genesys2/` |
| Pavona's targets built for Wren (the test ROM, tests, hello_world) | Bazel | `bazel-bin/external/pavona_pavona+/...`, still in this output base |
| The Verilator model | Bazel (FuseSoC), as a tool | `bazel-out/k8-opt-exec-*/bin/external/pavona_pavona+/hw/build.verilator_real/` |
| Host tools (opentitantool and the other tools the tests run) | Bazel, for the host | `bazel-out/k8-*/bin/external/pavona_pavona+/sw/host/...` |
| Downloaded repositories | Bazel | shared with the Pavona checkout (`--repo_contents_cache` in Pavona's `.bazelrc`) |

The Pavona checkout's own `bazel-*` links point at a different output base. Nothing built here
goes into the Pavona checkout, and `util/regen.sh` doesn't write there either.

**Host tools are built twice.** Pavona's host tools don't depend on the top: they take it at
run time with `--top`. But a build here compiles them again under `external/pavona_pavona+/`, in
this repository's output base, rather than reusing the Pavona checkout's. The cost is small,
measured on a 16-core host, building opentitantool and a Rust test harness (`usb_harness`) from
an empty output base with the remote cache off:
- about a minute in all: 742 actions, about 60 s wall time;
- 649 of the actions are third-party crates (about 220 s of summed run time). They are built once
  per output base, so only again after a clean or on a new machine;
- 93 are Pavona's own host code (about 55 s summed). These are rebuilt here after a Pavona change
  that touches them, as they are in the checkout.

Sharing a Bazel disk cache with the checkout (`--disk_cache`) saves nothing today: 0 hits. Each
C and Rust action takes the LLVM toolchain as an input. That toolchain's repository has a
different name depending on which module is the root (`+pavona_llvm+llvm_toolchain` in Pavona,
`pavona_pavona++pavona_llvm+llvm_toolchain` here), so every action key differs. Pavona's own
code could not hit in any case, since its paths differ. Using the checkout's built tools instead,
through a toolchain registered here, would avoid only opentitantool's part of the 93 actions.
Tests with their own Rust harness still build opentitanlib, and builds here would then depend on
the checkout's build being present and up to date. Neither is worth doing for now.

## Making your own out-of-tree top

1. **Module.** Copy `MODULE.bazel`, `.bazelrc` (set your top as `hw/top:top`), `.bazelversion`,
   `BUILD.bazel` and `third_party/`. `MODULE.bazel` repeats what Bazel takes only from the root module, so keep it
   in step with `../pavona/MODULE.bazel`: Pavona's `single_version_override`s (their patches
   must be in the root repository, hence the `third_party/*/patches` symlinks), Python 3.12 as
   the default, the whole `rust` extension block, and direct deps on the repositories that
   `.bazelrc` flags or your BUILD files name (`rules_rust`, `rules_fuzzing`, `platforms`,
   `rules_pkg`).
2. **Register the top** at the end of `MODULE.bazel`: `top.register(bazel_file =
   "//hw/top_<name>:defs.bzl", top_var = "<NAME>")` on Pavona's `top` extension.
3. **Start the top** from the in-tree top closest to yours (Wren started from Egret): copy
   `hw/top_<that>/` without its generated files, rename, and edit `data/top_<name>.hjson`.
   Symlink, rather than copy, files you keep unchanged.
4. **Generate.** Copy `util/regen.sh` and `util/fix-labels.py`, set `TOP` and `OWN`, and list
   your crossbars. `regen.sh` runs the `%_gen` steps of Pavona's `hw/Makefile` with the top
   directory here. `fix-labels.py` then makes the generated labels work from this repository:
   Pavona's as `@pavona_pavona//...`, and yours in `.bzl` strings as
   `str(Label("//hw/top_<name>/..."))`, since Pavona's rules resolve those strings in Pavona.
   Labels inside argument strings (`$(rootpath ...)`) are fixed by hand in the BUILD files.
5. **Top attributes** in `defs.bzl` (`pavona_top()`), as in Wren's: `instances`,
   `test_pinout`, `test_envs`, `test_rom_envs`, `top_cores` (a core file in the top's directory,
   so FuseSoC searches it), `ottf_no_nv_storage` for a small flash, and `bitstream_splice` to
   splice ROM and OTP images into a bitstream.
6. **Board.** Board-specific device libraries stay with the top (`sw/arch/`); Pavona has the
   exec env rule and device type for the board. The bitstream's `fusesoc_build` lists
   `@pavona_pavona//hw:cores` and your top's `cores`. Keep the top's `rtl_files` to what FuseSoC
   and Verilator read (cores, RTL, lint waivers, Vivado hooks, data), not `glob(["**"])`: with
   BUILD files, `defs.bzl` or documentation in it, every edit to those resynthesizes.
7. **Ignore the generated files** as `.gitignore` does here, then check that a fresh clone
   regenerates exactly the files you had: `git clone`, `util/regen.sh`, `diff -r`.
